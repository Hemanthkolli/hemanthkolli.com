Let the agent do the typing: connect Jira and Confluence to your AI assistant

22 Nov 2026 · 17 min read · #ai #productowner #mcp #copilot

Most Product Owners and Product Managers don't lose time on decisions. They lose it on clicks: creating epics, splitting features into stories, copying acceptance criteria, updating Confluence pages, and getting the backlog ready before PI Planning.

In an earlier LinkedIn post I shared the short version of a small hack: connect an AI agent to your backlog tools and let it draft while you decide. By "AI agent" I mean an AI assistant that can do things in other tools for you, not only chat.

A few people asked how to actually set it up, and whether it's safe for company data. This post is my attempt at a complete, honest answer. It's what worked for me; your company's policies come first.

You don't need to be an engineer for this. You'll copy a few commands into a terminal (the text window where you type instructions to your computer) and paste one settings file. I explain each piece as we go.

All the settings files from this post are also in a small companion repository (a shared online folder of files) that you can copy from: github.com/Hemanthkolli/jira-confluence-mcp-guide.

The idea in one minute

  1. Create a personal token for Jira and Confluence. A token is a long secret code, made for one purpose, that a program can use to sign in as you.
  2. Run a small MCP server on your own laptop. MCP (Model Context Protocol) is an open standard: a shared set of rules that lets AI assistants use other tools. Think of it as a universal plug socket. The "server" here is only a small program on your laptop, not a big machine somewhere. Its tools are "search Jira", "read a page", "create an issue" and so on.
  3. Connect it to the AI assistant you already have in your IDE, for example GitHub Copilot in VS Code. An IDE (integrated development environment) is the app developers write code in. VS Code is a free and popular one.
  4. Give it your planning input: meeting notes, a rough idea, last PI's objectives.
  5. Let it draft epics, stories, acceptance criteria and Confluence pages in your team's format. You review, adjust and decide.

An everyday comparison: it's like giving a capable new assistant a visitor badge. The badge (your token) only opens doors that you can open yourself, and you can limit it further. The assistant writes the drafts. You read them and sign them off.

The agent does the typing. You do the thinking.

How the pieces fit together

It helps to know where each piece runs before you decide whether this is acceptable for your organisation. There are four parts:

  1. Your IDE and its AI assistant. Based on what you ask (your "prompt"), the assistant decides which tool to use.
  2. The MCP server, a small Python program that the IDE starts on your laptop. The two talk over stdio (standard input/output): they pass text straight to each other, inside your laptop. So the server doesn't open a network port, which is a door that other computers could knock on.
  3. Jira and Confluence. The MCP server uses their REST APIs, the official way for programs (rather than people) to work with Jira and Confluence. The connection is HTTPS, which is encrypted, like the padlock in your browser. It uses your token, so it can see and do exactly what you can. No more, no less.
  4. The AI model service. This is the "brain", and it usually runs outside your laptop. The diagram calls it the LLM endpoint; LLM means large language model, the kind of AI behind Copilot. Your prompt, and whatever the tools fetched, are sent to the model so it can work out an answer.

Is our organisation's data safe?

Short answer: it can be. You need to be honest about the one place where data leaves your laptop, and put a few controls in place. Here is how I think about it.

What stays on your machine

  • The token. Only the local MCP server reads it. It's never sent to the AI model.
  • The connection to Jira and Confluence. It goes straight from your laptop to your company's Jira and Confluence. No outside company or hosted service sits in the middle.
  • Everything the assistant didn't fetch. The server doesn't copy your Jira or build its own searchable index of it. It only asks Jira or Confluence for data when the assistant needs something specific.

What does leave your machine

Be clear about this with your team and security colleagues: when the assistant reads an issue or a page, that text becomes part of the conversation. It is sent to the AI model service. That's how the model can summarise or rewrite it.

So the real question isn't "does data leave?" It's "is the AI service we use approved for this data?" Some things to check:

  • Use the company-approved assistant. With GitHub Copilot Business or Enterprise, GitHub states that your prompts and code are not used to train its models. Check your organisation's agreement and data-retention settings (how long data is kept) for the details. A personal or free plan usually comes with different terms.
  • Data classification. Don't point the agent at spaces or projects holding data your company labels confidential or restricted (HR, legal, customer personal data), unless that's explicitly allowed.
  • If nothing may leave at all, use a model your company hosts, or a local model (one that runs on your own laptop) that your IDE supports. The MCP setup in this post stays the same. Only the model's address changes.

One more honest note. mcp-atlassian, the server I use here, is a popular open-source project: its code is public, and its MIT licence lets anyone use it. It is not an official Atlassian product. Read its code, or ask your security team to review it. Then pin the version you approved, which means you always run that exact version (I show how below).

Atlassian also offers its own official MCP server for Cloud. It runs on Atlassian's side and uses OAuth instead of tokens. OAuth is the "Sign in with…" style of access: you approve it in your browser instead of copying a secret code. It's worth comparing if you're on Cloud.

Step 1: Create a token in Jira and Confluence

Which kind of token you need depends on how your company runs Atlassian, the company behind Jira and Confluence. If your Jira address ends in atlassian.net, you're on Cloud: Atlassian runs it for your company. Otherwise it's most likely Data Center (or the older Server), which your company runs itself.

Cloud

On Cloud, one API token covers both Jira and Confluence. "API token" is Atlassian's name for the secret code a program uses to sign in as you.

  1. Open id.atlassian.com → Security → API tokens.
  2. Click Create API token.
  3. Give it a clear name, e.g. mcp-laptop-2026, and pick the shortest expiry you can live with.
  4. Click Create, then Copy. You won't see the token again.

You'll also need the email address of your Atlassian account (used as the username), plus these URLs:

JIRA_URL=https://your-company.atlassian.net
CONFLUENCE_URL=https://your-company.atlassian.net/wiki

Atlassian also offers an "API token with scopes", which is limited to certain actions. The MCP server's documentation uses the classic API token for Cloud, so check its docs before you use a scoped one.

Data Center / Server

On Data Center you create a Personal Access Token (PAT) in each product separately. It does the same job as the Cloud API token. PATs are available from Jira 8.14 and Confluence 7.9 onwards.

  1. In Jira, click your avatar (top right) → Profile → Personal Access Tokens.
  2. Click Create token, give it a name and set Automatic expiry (for example 30 or 90 days).
  3. Click Create and copy the token right away.
  4. Repeat the same steps in Confluence: avatar → Settings or Profile → Personal Access Tokens.
JIRA_URL=https://jira.your-company.com
CONFLUENCE_URL=https://confluence.your-company.com

Some companies turn PATs off or limit their lifetime. If you don't see the menu, ask your Atlassian admins. Don't try to work around it.

Good habits for any token: treat it like a house key. Use one token per machine and purpose, with a short expiry. Never put it in a Git repository, and never paste it into a chat or a ticket. Revoke it (switch it off) on the same page the moment you don't need it.

Step 2: Install the MCP server without sudo (no admin rights)

sudo is the command for running something as an administrator on Linux and macOS. Many work laptops don't allow it, so this step avoids it.

The server is a Python package: a ready-made program written in the Python language. The easiest way to run it is with uv, a small tool that installs into your home folder. It downloads its own Python if needed, and doesn't need admin rights. Its uvx command runs a package in its own separate space (an "isolated environment"), so it doesn't get tangled up with other software on your laptop.

You type the commands below into a terminal: your terminal app on Linux, Terminal on macOS, PowerShell on Windows. Pick the tab for your computer.

Linux

Installs to ~/.local/bin (a folder inside your home folder), no sudo:

curl -LsSf https://astral.sh/uv/install.sh | sh

That command downloads an install script and runs it straight away ("piping it into a shell"). If your company doesn't allow that, use pip (Python's own installer) in user mode instead:

python3 -m pip install --user uv

Open a new terminal, then check it works and pin the version you've approved:

uvx mcp-atlassian@0.24.7 --help

macOS

With Homebrew, a popular free installer for Mac software (no sudo):

brew install uv

Without Homebrew, the installer puts it in ~/.local/bin:

curl -LsSf https://astral.sh/uv/install.sh | sh

Open a new terminal, then check it works and pin the version you've approved:

uvx mcp-atlassian@0.24.7 --help

Windows

In PowerShell, as your normal user (not "Run as administrator"). It installs to %USERPROFILE%\.local\bin, a folder inside your user folder:

powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"

Or with winget, the Windows app installer, which installs it for your user only:

winget install --id=astral-sh.uv -e

Open a new terminal, then check it works and pin the version you've approved:

uvx mcp-atlassian@0.24.7 --help

Why pin the version? uvx mcp-atlassian without a version number always fetches the newest release. Pinning means a new release only reaches your laptop after you've decided to upgrade. It's a small but real safeguard against a bad update slipping in, which security people call a "supply-chain" risk. 0.24.7 was current when I wrote this; check PyPI, the public catalogue of Python packages, for newer versions.

Behind a corporate proxy (a company gateway that all web traffic passes through)? Set HTTPS_PROXY in the same env block as the other settings; you'll see that block in step 4. If your company has added its own security certificates to your operating system, they're picked up automatically.

Step 3: Keep the token out of config files

Many examples online put the token straight into a settings file (a JSON file). That's how tokens end up in Git history and screenshots, where other people can find them. Better options, from my favourite down:

  1. Let the IDE ask for it. VS Code and Visual Studio can ask for the token once and store it encrypted. Step 4 shows how.
  2. Read it from your keychain when it's needed. A keychain is the password safe built into your computer. The server supports *_COMMAND settings: instead of the token itself, you give it a command that looks up the token and hands it over.
  3. A private env file (a small text file of settings) in your home folder, readable only by you, and never inside a project folder.

Linux

Many Linux desktops have a password safe called the GNOME keyring, which you use through the secret-tool command. Store the token once. The command asks you for the value, so the token never ends up in your shell history (the terminal's record of past commands):

secret-tool store --label="Jira token" service mcp-atlassian account jira

Then, in the server's env settings, use the command instead of the token:

"JIRA_API_TOKEN_COMMAND": "secret-tool lookup service mcp-atlassian account jira"

If secret-tool isn't installed and you can't install it, use an env file only you can read:

mkdir -p ~/.config/mcp-atlassian
touch ~/.config/mcp-atlassian/env && chmod 600 ~/.config/mcp-atlassian/env

macOS

macOS has a keychain command built in. Store the token once. The -w at the end makes it ask you for the value:

security add-generic-password -a "$USER" -s mcp-atlassian-jira -w

Then, in the server's env:

"JIRA_API_TOKEN_COMMAND": "security find-generic-password -s mcp-atlassian-jira -w"

Windows

The simplest secure option on Windows is to let VS Code or Visual Studio ask for the token (step 4). If your password manager has a command-line tool (one you can use from the terminal), the command approach works too. For example, with 1Password:

"JIRA_API_TOKEN_COMMAND": "op read \"op://Work/Jira token/credential\""

On Windows, use double quotes inside the command. For a .bat or PowerShell helper script, put cmd /c or powershell -NoProfile -Command in front of it.

For Data Center, the settings are named JIRA_PERSONAL_TOKEN_COMMAND and CONFLUENCE_PERSONAL_TOKEN_COMMAND.

Step 4: Connect your IDE

Every IDE uses the same server and the same settings. Only the settings file is different, so pick the tab for the app you use. The examples use Cloud, with read-only mode on and a filter that limits the agent to one project. For Data Center, replace JIRA_USERNAME + JIRA_API_TOKEN with JIRA_PERSONAL_TOKEN (same for Confluence).

VS Code + GitHub Copilot

  1. Open the Command Palette (VS Code's search box for commands) and run MCP: Open User Configuration, which applies to all your projects. Or create .vscode/mcp.json inside one project.
  2. Paste this. The inputs block makes VS Code ask for the token once and store it encrypted, so it's never written in the file:
{
  "inputs": [
    {
      "id": "atlassian-token",
      "type": "promptString",
      "description": "Atlassian API token",
      "password": true
    }
  ],
  "servers": {
    "atlassian": {
      "type": "stdio",
      "command": "uvx",
      "args": ["mcp-atlassian@0.24.7"],
      "env": {
        "JIRA_URL": "https://your-company.atlassian.net",
        "JIRA_USERNAME": "you@your-company.com",
        "JIRA_API_TOKEN": "${input:atlassian-token}",
        "CONFLUENCE_URL": "https://your-company.atlassian.net/wiki",
        "CONFLUENCE_USERNAME": "you@your-company.com",
        "CONFLUENCE_API_TOKEN": "${input:atlassian-token}",
        "READ_ONLY_MODE": "true",
        "TOOLSETS": "default",
        "JIRA_PROJECTS_FILTER": "ABC",
        "CONFLUENCE_SPACES_FILTER": "TEAM"
      }
    }
  }
}
  1. Click Start, which appears above the server name in the file, or run MCP: List Servers. VS Code asks for the token the first time.
  2. Open Copilot Chat and switch the mode to Agent, the mode where Copilot can use tools and not only answer. Then click the tools icon. You should see the Jira and Confluence tools.

With Copilot Business or Enterprise, an organisation admin has to allow MCP servers in Copilot. If the tools don't appear, that policy is the first thing to check.

Visual Studio

Visual Studio 2022 (version 17.14 and later) supports MCP servers in Copilot's agent mode. It uses the same servers format as VS Code.

  1. Create %USERPROFILE%\.mcp.json for all solutions ("solution" is Visual Studio's word for a project), or .mcp.json next to your solution file for one solution.
  2. Paste the same inputs and servers block as in the VS Code tab.
  3. Open Copilot Chat, select Agent mode, and enable the Atlassian tools in the tools picker.

If Visual Studio can't find uvx, use the full path: C:\\Users\\<you>\\.local\\bin\\uvx.exe. Remember the double backslashes: JSON files need them.

JetBrains (IntelliJ, PyCharm, Rider, …)

There are two common routes:

  • JetBrains AI Assistant: Settings → Tools → AI Assistant → Model Context Protocol (MCP) → Add, then paste the JSON below.
  • GitHub Copilot plugin: in Copilot Chat, switch to Agent mode, click the tools icon → Add more tools…. This opens Copilot's mcp.json, which uses the same servers format as VS Code.
{
  "mcpServers": {
    "atlassian": {
      "command": "uvx",
      "args": ["mcp-atlassian@0.24.7"],
      "env": {
        "JIRA_URL": "https://your-company.atlassian.net",
        "JIRA_USERNAME": "you@your-company.com",
        "JIRA_API_TOKEN_COMMAND": "security find-generic-password -s mcp-atlassian-jira -w",
        "READ_ONLY_MODE": "true",
        "TOOLSETS": "default",
        "JIRA_PROJECTS_FILTER": "ABC"
      }
    }
  }
}

This example reads the token from the macOS keychain (step 3). On Linux or Windows, use the command for your system from step 3 instead.

Cursor

Create ~/.cursor/mcp.json for all projects, or .cursor/mcp.json in one project. Cursor uses the mcpServers format, the same as the JetBrains tab. Then enable the server under Settings → MCP.

Cursor has no password prompt like VS Code, so use the keychain command from step 3 rather than writing the token into the file.

Claude Code

One command. It's saved in your user settings and works in every project:

claude mcp add atlassian --scope user \
  -e JIRA_URL=https://your-company.atlassian.net \
  -e JIRA_USERNAME=you@your-company.com \
  -e "JIRA_API_TOKEN_COMMAND=security find-generic-password -s mcp-atlassian-jira -w" \
  -e READ_ONLY_MODE=true -e TOOLSETS=default -e JIRA_PROJECTS_FILTER=ABC \
  -- uvx mcp-atlassian@0.24.7

Run claude mcp list to check it's connected. Claude Code asks before every tool call unless you allow it. Leave write tools (the ones that create or change things) on "ask".

Step 5: First test, read-only

Start with questions that only read. If these work, the connection, the token and the filters are set up right:

  • "List the open stories in project ABC assigned to me, with status and story points."
  • "Summarise the Confluence page 'Team working agreement' in five bullet points."
  • "Which epics in ABC have no stories yet?"

Also check that the filters work. Ask about a project that's not in JIRA_PROJECTS_FILTER. The agent shouldn't be able to see it.

Worked example: PI Planning prep with GitHub Copilot

Here's the flow I use in VS Code with Copilot in agent mode. Nothing is written to Jira until the last step, and only after I've read the drafts.

1. Teach it your conventions once

Create a file in your workspace (the folder you have open in VS Code), for example backlog-conventions.md. It's a plain text note of your team's rules, so you don't have to repeat them in every request:

# Backlog conventions (team ABC)
- Story title: "As a <role>, I want <goal>" (max 80 characters)
- Description sections: Context, Scope, Out of scope
- Acceptance criteria: Given / When / Then, 3 to 6 per story
- Labels: pi-2027-1, plus one of: backend, frontend, platform
- Story points: leave empty; the team estimates in refinement
- Language: plain English, no internal code names

2. Ask for drafts, not actions

youRead #file:meeting-notes-2026-11-20.md and #file:backlog-conventions.md. Then look at the open epics in Jira project ABC. Draft one new epic and the stories needed for the "supplier onboarding" topic. Show me the drafts as Markdown. Don't create anything in Jira.

copilotCalls jira_search (read-only) and checks existing epics, then returns a Markdown draft: one epic, six stories, acceptance criteria in Given/When/Then, and a note that two of the stories overlap with the existing epic ABC-412.

The #file: part tells Copilot to read that file from your workspace.

3. Review and adjust like you would with a colleague

youMerge stories 3 and 4. Story 6 belongs in ABC-412, so move it there instead. Make the acceptance criteria of story 2 testable; "fast" isn't measurable.

4. Only then, let it create

Switch the server to allow writes (see the next section), then:

youCreate the epic and the five stories in ABC exactly as in the final draft. Link the stories to the epic. Then list the new issue keys.

copilotVS Code shows a confirmation for each jira_create_issue call with the exact fields. You click Continue only for the ones you've checked.

The same works for Confluence: "Draft the PI objectives page in the format of last PI's page, but don't publish it", then review, then create it.

Turning on writes, carefully

  • Change READ_ONLY_MODE to "false" only for the session where you create things. Set it back afterwards.
  • Keep JIRA_PROJECTS_FILTER limited to your own project, so a mistake can't reach other teams' boards.
  • For even tighter control, allow only the tools you need: "ENABLED_TOOLS": "jira_search,jira_get_issue,jira_create_issue".
  • Never turn on "auto-approve" for write tools in your IDE. Reading each confirmation takes seconds; undoing 40 wrongly created issues doesn't.

Troubleshooting

The IDE says uvx is not found
IDEs started from a menu often don't see your terminal's PATH, the list of folders where your computer looks for programs. Use the full path instead: ~/.local/bin/uvx on Linux and macOS (or /opt/homebrew/bin/uvx with Homebrew), and C:\Users\<you>\.local\bin\uvx.exe on Windows.
401 Unauthorized
This means Jira or Confluence didn't accept your sign-in. On Cloud, check you used your email as the username, and an API token, not your password. On Data Center, use JIRA_PERSONAL_TOKEN and no username. Also check the token hasn't expired.
SSL or certificate errors
These are problems checking that the connection is secure. Company certificates installed in your operating system are used automatically. If it still fails, ask IT for the right CA bundle (the file of certificates your company trusts) rather than turning the check off.
The tools don't show up in Copilot
Make sure you're in Agent mode, the server is started (MCP: List Servers), and your organisation allows MCP servers in Copilot.
The agent sees too much or too little
Check JIRA_PROJECTS_FILTER and CONFLUENCE_SPACES_FILTER (project or space keys, separated by commas). Remember too that the token can only see what you can see.

Checklist

  • The AI assistant is approved by my organisation for this kind of data
  • Token has a short expiry and is stored in a keychain or IDE prompt, not in a file in Git
  • MCP server version is pinned and reviewed
  • READ_ONLY_MODE=true by default
  • Projects and spaces are filtered to what I actually need
  • Tool confirmations are on in the IDE, and nothing is auto-approved for writes
  • Conventions file written once, reused every time
  • I review every draft before anything is created

I'm still learning what works best here, and tools in this space change quickly, so menu names may have moved by the time you read this. If something is out of date or you've found a better way, please tell me.
